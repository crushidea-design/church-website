## 우선순위별 개선 항목

### P0-1. RAAH 관리자 판정에서 사용자 수정 가능 메타데이터 제거

**근거:** `netlify/functions/raah-notes.mts:151`, `raah-management.mts:217`, `raah-calendar.mts:108`, `raah-ai-assist.mts:66`에서 Supabase `user_metadata.role === 'admin'`을 관리자 조건으로 허용한다. Firebase 검증 이후 Supabase 토큰도 허용하는 전환 경로가 남아 있다.

Supabase 공식 문서는 user_metadata가 사용자에 의해 수정될 수 있으므로 인가에 사용하지 말라고 명시한다. [공식 사용자 문서](https://supabase.com/docs/guides/auth/users).

**영향:** 유효한 일반 Supabase 계정을 가진 사람이 해당 메타데이터를 수정할 수 있는 운영 구성이라면 RAAH 관리자 API 접근으로 이어질 수 있다. 실제 가입·계정 상태는 미확인이다. SQL의 app_metadata 조건이 안전하더라도 서버가 service-role 자격으로 실행하는 API의 잘못된 인가를 대신 막아주지는 않는다.

**계획:** 프로젝트 지침대로 Firebase ID 토큰 검증과 서버 관리자 확인을 공통 모듈로 통일한다. Supabase 인증 호환 경로의 실제 사용 여부를 조사하고 제거한다. 이행 기간이 꼭 필요하면 서버가 관리하는 역할만 허용한다. 관리자 이메일 예외와 이메일 검증 정책도 함께 정리한다.

**완료 기준:** 토큰 없음·만료·일반 회원·위조 역할·권한 회수 사용자는 거절되고 승인된 관리자만 접근한다. 네 API 모두 같은 테스트를 통과하며 기존 암호화 저장/조회는 유지된다.

### P0-2. 목양 원문의 외부 전송 경로 차단

**근거:** `raah-ai-assist.mts:121` 이후 프롬프트에 성도 이름과 rawMemo를 넣고, 147행 이후 Gemini API에 전송한다. `src/pages/AdminPastoralNotes.tsx:590`에서 이를 호출한다. 이는 “목양·심방 데이터를 외부 API에 노출하지 않는다”는 프로젝트 지침과 충돌한다.

**계획:** 먼저 해당 원문 전송 기능을 서버에서 차단하고 UI에서도 안내한다. 외부 전송 없이 작성할 수 있는 수동 정리 양식으로 대체한다. 이름만 삭제하면 충분히 비식별화된다고 간주하지 않는다. 외부 응답 전체를 기록하는 오류 로그도 구조화된 오류 코드 중심으로 바꾼다.

**추가 확인:** `raah-calendar.mts:297`, `:306`, `:506`은 일정 memo를 Google Calendar description으로 보낸다. 일정 메모가 목양 상세 기록을 포함할 수 있는지 확인하고, 전송 가능한 일정 필드를 명시적으로 제한한다.

**완료 기준:** 테스트용 식별 표식이 포함된 목양 원문이 외부 HTTP 요청이나 로그로 나가지 않는다. 일정 연동도 승인된 최소 필드만 전송한다.

### P0-3. 첨부파일과 가정예배 사진 권한 축소

**근거:** `storage.rules`의 pdfs/materials/sermons 경로는 로그인만 하면 임의 파일을 덮어쓰거나 삭제할 수 있다. 읽기는 공개다. family-worship 사진도 모든 로그인 사용자에게 읽기가 허용된다.

**영향:** 게시글 수정 권한과 파일 수정 권한이 분리되어 있다. Firestore에서 제한된 설교나 가정 정보라도 첨부파일 경로의 공개 범위가 다를 수 있다.

**계획:** 업로더 UID·게시글 식별자를 기준으로 경로와 소유권을 정리한다. 기존 파일은 참조와 소유자를 매핑한 뒤 단계적으로 이전한다. 읽기 권한은 게시글/가정·담당교사 범위와 맞춘다. 이미 배포된 다운로드 토큰 URL은 규칙 수정만으로 회수됐다고 간주하지 않고 별도 점검한다.

**완료 기준:** 다른 계정의 파일 덮어쓰기·삭제가 거절되고, 관계없는 계정의 가족 사진 읽기가 거절된다. 기존 정상 첨부파일은 계속 열리며, 공유 URL 처리 방침도 검증된다.

### P1-1. 게시글의 실제 공개 정책을 보안 규칙에 반영

**근거:** `firestore.rules:99`의 canReadPostData는 sermon 여부와 회원 역할/작성자만 판정한다. 모델에 있는 isPublished, scheduledAt, targetUserIds, isArchived는 읽기 판정에 사용되지 않는다. 다른 카테고리는 이 함수에서 공개 읽기로 처리된다.

**계획:** 각 필드가 보안 경계인지 화면 정렬/표시용인지 먼저 명확히 정의한다. 비공개·예약·대상자 제한을 의도한 필드는 서버/규칙에서 강제한다. 목록 쿼리, 상세 조회, 본문/PDF 조각, 댓글, 홈 요약 문서까지 동일 정책을 적용한다. 기존 필드 누락 문서의 기본값도 정한다.

**완료 기준:** 비공개/예약/대상자 제한 문서를 직접 SDK로 조회해도 비인가 접근이 거절된다. 공개 목록 쿼리는 정상 작동한다. 현재 운영에 제한 문서가 실제 존재하는지는 별도 확인한다.

### P1-2. 댓글 저장과 집계의 정합성 보장

**근거:** `src/pages/PostDetail.tsx:262` 및 `:387` 부근에서 댓글 생성/삭제와 posts.commentCount 갱신이 별도 요청이다. `firestore.rules:312`는 로그인 사용자의 ±1 집계 변경을 허용하지만 실제 댓글 변경과 연결하지 않는다.

**계획:** 댓글 생성/삭제와 집계를 원자적으로 처리하는 서버 경로 또는 검증 가능한 트랜잭션을 설계한다. 서버 집계 방식이면 재시도 중복 처리를 막는다. 단순 writeBatch 추가만으로 인가 문제가 해결됐다고 보지 않는다. 기존 집계 불일치는 별도의 비교·복구 작업으로 다룬다.

**완료 기준:** 저장 중 실패·중복 요청·동시 작성/삭제 후 실제 댓글 수와 집계가 일치한다. 집계만 직접 조작하는 요청은 거절된다.

### P1-3. RAAH 목록·대시보드의 데이터 증가 대응

**근거:** `raah-management.mts:631`의 bootstrap은 성도·심방 로그·출석 기록을 폭넓게 조회한다. 일정은 날짜 오름차순 limit=100이며 이후 페이지 경로가 해당 초기 조회에 없다. `raah-notes.mts:247` 목록도 명시적 페이지네이션 없이 조회한다.

**영향:** 데이터가 증가하면 응답이 무거워지고, 조회 상한으로 인한 누락을 전체 결과처럼 취급할 수 있다. 일정이 많이 쌓이면 과거 100건이 먼저 선택되어 필요한 이후 일정이 빠질 수 있다.

**계획:** 초기 응답은 요약과 선택 기간 데이터로 제한한다. 성도/기록은 커서 기반 목록, 출석은 기간별 서버 집계, 일정은 보이는 달/주 범위 조회로 분리한다. 목양 상세는 필요한 시점에만 조회한다.

**완료 기준:** 100건 초과 일정과 대량 출석·기록의 테스트 데이터에서 누락 없이 탐색되고, 요약 수치가 원본과 일치한다. 상한 적용 시 hasMore/total 등으로 명시한다.

### P1-4. 예약 알림·캘린더 동기화의 중복 실행 방지

**근거:** `scheduled-notifications.mts`는 pending을 읽고 전송한 뒤 sent로 갱신한다. `server.ts:144`에도 같은 시간 주기의 발송 작업이 있다. `raah-calendar.mts:479` 이후 Google 이벤트 생성 성공과 Supabase external_id 저장 사이에 실패 구간이 있다.

**계획:** 작업별 고유 키, 실행권 획득, 처리 상태와 재시도 정책을 도입한다. 캘린더는 동일 내부 일정이 재시도되어도 같은 외부 이벤트에 대응하도록 설계한다. 개발 서버 예약 작업은 기본 비활성화하고 테스트 프로젝트에서만 명시적으로 켠다.

**완료 기준:** 동시 실행·발송 직후 상태 저장 실패·외부 생성 직후 실패를 주입한 테스트에서 중복 처리와 유실을 감지/복구한다. 공급자의 보장 범위를 넘어 정확히 한 번 전송된다고 가정하지 않는다.

### P1-5. 보안·실행 동작을 검증하는 테스트 추가

**근거:** 123개 테스트는 통과하지만 Firestore/Storage 에뮬레이터 권한 테스트와 실제 브라우저 흐름 검증은 현재 구성에 없다. `AdminPastoralNotes.schedule.test.ts`, `PdfCanvasViewer.test.ts`에는 소스 문자열 포함 여부를 확인하는 테스트가 있다. `.github/workflows/ci.yml`에는 build 단계가 없다.

**계획:** P0 항목의 거절 테스트를 가장 먼저 추가한다. API 인증·입력 검증·암호화 왕복 및 변조 거절, 댓글 실패/재시도, 부모·교사·관리자 역할 흐름, 일정 저장/수정에 집중한다. 문자열 테스트는 동작 검증으로 필요한 부분부터 대체한다. CI에 build를 추가하고 PR 필수 검사 설정은 운영 설정에서 확인한다.

**완료 기준:** 잘못된 권한이나 부분 저장을 의도적으로 넣으면 테스트가 실패한다. 모든 PR에서 타입 검사·린트·테스트·빌드가 수행된다.

### P2-1. 인증·캐시의 수명과 로그아웃 정리

**근거:** `src/lib/auth.tsx`는 역할을 sessionStorage에서 재사용한다. `src/store/useStore.ts`는 묵상 진행/내용을 영속 저장하고, `src/lib/firebase.ts:145`의 logout은 signOut만 호출한다. 묵상 키에는 UID가 들어 있으므로 단순히 날짜만 같아서 계정 간 혼합된다고 판단하지는 않는다.

**계획:** 역할 변경을 반영하는 갱신/만료 정책과 로그인 변경 시 비동기 응답 무효화를 도입한다. 개인 캐시는 로그아웃 시 삭제하고 저장 기간과 범위를 제한한다. 공용 콘텐츠 캐시와 개인 데이터를 분리한다. 서버 인가가 항상 최종 권한 판단을 맡게 한다.

**완료 기준:** 계정 전환·권한 회수·공용 기기 로그아웃 후 이전 개인 데이터가 화면이나 영속 캐시에 남지 않는다.

### P2-2. 큰 파일과 반복 코드를 기능 단위로 분리

**근거:** AdminPastoralNotes 1,818행, raah-management 1,137행, WordFruitSettings 1,071행, NextGenerationAdmin 988행, EditPost 982행이다. RAAH 인증/환경변수/응답 처리와 개발 서버·Netlify 함수 로직도 중복된다.

**계획:** 먼저 공통 서버 인가/응답/외부 요청 처리를 추출하고 계약 테스트를 붙인다. 이후 RAAH를 성도·출석·심방·일정의 API/폼/조회 훅으로 분리한다. 작성/수정 페이지는 첨부파일과 저장 처리부터 공유한다. 프레임워크나 상태관리 도구를 한 번에 교체하지 않는다.

**완료 기준:** 기능별 변경 범위가 줄고 개발/배포 API 계약이 일치한다. 특히 `npm run dev`의 server.ts에 없는 RAAH 경로를 로컬에서도 검증할 수 있도록 Functions 실행 또는 명시적 프록시를 마련한다.

### P2-3. 타입·린트와 실제 초기 로딩 개선

**근거:** tsconfig에 strict가 설정되어 있지 않고 린트 경고는 428개다. NextGeneration은 내부 여러 화면을 정적 import한다. 공통 SiteCmsProvider는 앱 전체를 감싼다.

**계획:** API 경계에 런타임 검증과 명시적 DTO를 도입한다. 인증·목양·파일 처리부터 any와 Hook 경고를 줄이고 strict 옵션을 단계적으로 적용한다. 이후 다음세대 편집/마이페이지/데모 등 비초기 화면을 지연 로딩하고, 필요 없는 CMS 구독을 화면 범위로 제한한다. 성능은 모바일 네트워크에서 첫 화면과 주요 사용자 흐름을 측정한 뒤 조정한다.

**완료 기준:** 신규 경고를 늘리지 않고 핵심 경계의 타입을 명시한다. 필수 코드 다운로드와 Firestore 읽기가 줄어드는지 전후 측정한다. 청크 경고 임계값을 올리는 것으로 완료 처리하지 않는다.

### P2-4. 운영 정보와 비밀정보 로그 정리

**근거:** `server.ts:132` 이후 초기화 오류 시 서비스 계정 문자열 앞부분을 출력한다. README는 AI Studio 초기 템플릿 안내에 머물러 있다. public 서비스 워커는 앱과 별도로 Firebase SDK 버전/구성을 관리한다.

**계획:** 자격증명 일부 출력도 제거하고 오류 코드와 요청 식별자만 남긴다. 개발/운영 실행 방법, 필요한 환경변수의 이름, 규칙/SQL 적용 순서, 암호화 키 보관·교체·복구 절차, 알림 운영과 장애 대응을 문서화한다. 서비스 워커 변경 시 알림·배지·클릭 이동을 회귀 검증한다. 의존성 취약 여부는 lockfile 감사 결과로 별도 확인하며 버전이 오래됐다는 이유만으로 취약하다고 단정하지 않는다.

**완료 기준:** 새 환경에서 문서대로 개발/검증이 가능하고, 오류 로그에 키·목양 원문이 없다. 테스트 데이터로 암호화 기록 복구 절차를 확인한다.
