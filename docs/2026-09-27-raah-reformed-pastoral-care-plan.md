이 문서는 방향을 구체화한 제안이다. 기록 권한, 성찬 참여 감독, 입교 및 권징의 실제 기준은 해당 교회의 신앙고백과 교회정치, 정당한 위임에 따라 확정한다. 계획서 작성·업로드는 기능 구현, 데이터 이전, 권한 확대 또는 배포 승인을 의미하지 않는다. 모든 예시는 가상이며 실제 성도의 기록을 포함하지 않는다.

## 1. 이번 계획의 핵심 결정

현재의 성도 명부·출석·심방 기록·후속 조치·사역 일정을 버리지 않는다. 이 기능들을 성찬 목양과 정기적인 돌봄이라는 실제 목회 흐름으로 연결한다. 개혁주의 정체성은 화면에 고백문을 장식하는 방식보다, 무엇을 살피고 누구에게 책임을 맡기며 어떤 판단을 앱이 하지 않는지에 드러나야 한다.

개발 순서는 다음과 같다.

| 단계 | 목표 | 공개·운영 범위 |
| --- | --- | --- |
| P0 | 신뢰할 수 있는 데이터 상태와 목양 전용 접근 경계 확보 | 기존 기능의 안전한 개선 |
| P1A | 성찬 목양 최소 기능을 한 목양자가 검증 | 제한된 시범 사용 |
| P1B | 성찬 전후의 후속 돌봄, 반복 주기, 실제 참여 기록 연결 | 성찬 목양 정식 사용 |
| P2 | 언약 가정과 정기 가정심방 | 성도·가정 중심 목양 확장 |
| P3 | 세례·교리교육·입교 여정, 말씀·기도의 목양 연결 | 교육과 돌봄의 연속성 확보 |
| P4 | 정당하게 위임된 장로의 공동 목양 | 권한·감사·인수인계 검증 후 |
| P5 | 당회 기록과 권징·회복 | 별도 승인·설계가 필요한 장기 과제 |

첫 출시의 핵심은 `성찬 목양 주기 생성 → 대상 확인 → 대화와 권면 기록 → 후속 돌봄 → 다음 확인`이다. 권징록, 성도용 앱, 자동 영성 분석, 전 교인 점수표를 함께 만들지 않는다.

## 2. 신학적 원칙과 제품 설계의 경계

### 2.1 은혜의 방편을 중심에 둔다

웨스트민스터 소요리문답 88–91문은 말씀·성례·기도와 성령의 역사를 함께 설명한다. 앱의 출석률이나 기록량을 은혜의 효력으로 취급하지 않는다. 설교를 듣는 생활, 성례, 기도, 권면과 위로를 돕는 데 기록을 사용한다. 교제와 가정교육 역시 중요하지만 모든 활동을 동일한 종류의 은혜의 방편이라고 뭉뚱그려 분류하지 않는다. [T1]

제품 원칙: `참석 사실 ≠ 믿음의 크기`, `교육 이수 ≠ 신앙고백`, `상담 기록량 ≠ 목양의 충실함`.

### 2.2 성찬 준비는 자기 의의 증명이 아니다

하이델베르크 요리문답 81문은 죄에 대한 슬픔, 그리스도의 용서에 대한 신뢰, 믿음과 삶이 새로워지기를 바라는 마음을 함께 다룬다. 대요리문답 172문은 연약하고 의심하는 신자를 성찬에서 무조건 멀어지게 하지 않는다. [T2][T3]

제품 원칙: 확신의 부족, 낙심, 질병으로 인한 결석을 자동적인 참여 제한 사유로 변환하지 않는다. `성찬 적합`, `영성 위험`, `믿음 부족` 점수나 신호등은 만들지 않는다. 회개와 믿음을 살피되 복음의 위로가 문답과 후속 행동에 반드시 포함되도록 한다.

### 2.3 성찬의 거룩함과 교회의 감독도 약화시키지 않는다

하이델베르크 82문, 대요리문답 173문은 교회의 감독을 실제적인 것으로 다룬다. 그러므로 앱이 아무 판단도 하지 않는다는 이유로 교회의 정당한 판단 자체를 없애서는 안 된다. 다만 목양자의 대화 기록과 교회가 정식으로 내린 결정은 구별해야 한다. [T2][T3]

제품 원칙: 앱은 참여 제한을 새로 결정하지 않는다. 교회의 기존 결정을 기록할 경우 근거 문서, 결정 주체, 날짜와 효력 범위를 갖추고 권한 있는 사람이 확인한다. 심방 완료 버튼이나 후속 조치 완료 버튼으로 공식 상태를 바꿀 수 없다.

### 2.4 개인과 가정을 함께 돌본다

웨스트민스터 신앙고백 25.2와 28.4는 가시적 교회와 신자의 자녀 및 세례를 다룬다. 이 점을 반영해 가정과 자녀의 교육을 목양 구조에 연결한다. 그러나 가정 전체를 한 사람의 영적 상태로 대표시키거나 부모의 성찬 관련 판단을 자녀에게 전이시키지 않는다. [T4]

제품 원칙: 개인 기록이 기본 단위이고 가정은 관계와 돌봄의 단위다. 독신, 홀로 신앙생활하는 사람, 비신자 가족과 사는 성도도 동일하게 배려한다.

### 2.5 교회별 시행 방식과 고백적 원칙을 구별한다

URCNA 교회정치 14조는 장로의 가정심방·교리교육·성례 감독 등을, 45조는 성찬 참여 감독을 다룬다. 이는 개혁교회 직무 구조를 참고하는 일차 자료이지, 모든 한국 개혁교회에 동일한 심방 주기와 절차가 의무라는 근거는 아니다. [T5]

제품 원칙: 성찬 전 특정 날짜에 전 교인 심방을 완료해야 한다는 규칙을 고정하지 않는다. 교회가 성찬 빈도, 정기심방 간격, 성찬 전 특별심방 여부, 방문 교인 확인 절차를 설정한다.

## 3. 현재 코드에서 출발해야 할 지점

다음은 위 기준 커밋의 코드에서 확인한 구조다. 운영 서버와 실제 DB가 현재 정상이라는 확인과는 구별한다.

| 영역 | 현재 구조 | 개선 방향 |
| --- | --- | --- |
| 전체 화면 | `AdminPastoralNotes.tsx`가 상태·로딩·탭·대시보드를 조정 | 필요한 부분부터 훅과 기능별 화면으로 분리 |
| 성도 | `RaahMember`에 이름·연락처·직분·구역·활성 상태 등 존재 | 세례·입교·성찬회원 기록을 별도 구조로 추가 |
| 출석 | 예배 유형, 출석 여부, `communionParticipated` 존재 | 사실 기록과 성찬 목양 진행 상태를 분리 |
| 기록 | 요약과 암호화된 민감 본문을 구별 | 성찬 문답을 기존 기록에 연결하되 권한을 강화 |
| 후속 조치 | `sourceType: 'visitation'` 중심 완료 기록 | 기한·담당자·상태를 가진 돌봄 할 일로 확장 |
| 일정 | 수동·Google 일정, 시작·종료일, 완료 상태 | 목양 과제와 일정의 연결 관계만 추가 |
| 인증 | Firebase 신원 검증 후 홈페이지 관리자 역할 등 확인 | 별도의 목양 접근 승인과 기록별 권한 확인 |
| 저장 | Netlify API 뒤에서 Supabase 사용, 구형 Firestore 호환 존재 | 신규 민감 기능은 Supabase 실패 시 차단, 평문 우회 금지 |

코드 근거: [C1][C2][C3][C4].

특히 다음 사항은 새 기능보다 먼저 다뤄야 한다.

1. 현재 홈은 `활성 인원 - 출석 인원`으로 미출석을 계산한다. 새 화면에서는 미조회·미기록·실제 결석을 구별해야 한다. 로딩 실패를 0명이나 전원 결석으로 표시하지 않는다. #100 이후 성도 상세의 주간 출석에는 `미기록` 표시가 생겼으나, 홈 집계(`absentCount`)는 여전히 차감 방식이다. [C1]
2. 현재 로딩 흐름은 일부 404·503 오류에서 Firestore 호환 모드로 전환한다. 신규 성찬 기록에서는 장애·권한 오류·설정 누락을 분리하고, 다른 저장소에 민감 내용을 자동 저장하지 않는다. [C1]
3. 현재 서버의 `requireRaahAdmin`은 홈페이지 관리자 역할을 검사하며 `raah-management`, `raah-notes`, `raah-calendar`, `raah-ai-assist`(외부 AI는 이미 410으로 차단됨)가 공통으로 사용한다. `직분`이라는 성도 명부 문자열과 로그인 사용자의 실제 직무·열람 권한은 다른 개념이다. [C2][C3]
4. 현재의 암호화 구조가 명부·공개 요약·일정 등 모든 필드를 암호화한다는 뜻은 아니다. `암호화 저장` 표시는 보호 범위를 정확히 설명해야 한다. [C2][C4]
5. 현재 서버는 Supabase를 `/rest/v1/<table>` 단건 호출로 사용하며, 여러 쓰기를 묶는 트랜잭션 경로가 없다. 신규 기능의 원자성 요구는 섹션 12.5의 방식으로 해결한다. [C4]

## 4. 사용자와 권한에 대한 전제

첫 기능은 승인된 목양자 한 명이 사용한다. 성도에게 직접 질문지를 제출하게 하거나 자신의 영적 상태를 평가하도록 하는 포털은 만들지 않는다. 이후 장로를 초대하더라도 홈페이지 관리자 계정을 공유하지 않는다.

목양 소프트웨어 사용 권한이 교회정치상의 권한을 만들어 주지는 않는다. 당회나 교회의 위임을 받지 않은 사용자가 앱에서 스스로 성찬 감독자·권징 결정자가 될 수 없다. 현재 정식 당회 업무를 수행할 수 없는 환경에서는 개인 목양 준비·기록·후속 돌봄만 사용한다.

`목양 담당자`는 소프트웨어상 접근 주체이고, `교회 결정 주체`는 교회정치상의 권한이다. 두 개념을 데이터와 문구에서 분리한다.

## 5. 정보구조와 화면 변경

### 5.1 P1에서 적용할 최소 변경

기존 메뉴를 전면 교체하지 않는다. 데스크톱에는 `홈 / 성도 / 성찬 목양 / 출석 / 사역일정 / 기록`을 두고 `이전 기록`은 별도 보관 영역에서 접근하도록 한다. 기존 자료 접근 경로는 유지한다.

모바일은 탭을 일곱 개로 늘리지 않는다. `홈 / 성도 / 성찬 목양 / 기록 / 더보기`의 다섯 진입점을 제안한다. 출석·일정·이전 기록은 더보기에서 접근하되, 홈의 출석 체크와 일정 등록 바로가기는 유지한다. 출석 사용 빈도가 높으면 시범 사용 결과로 고정 탭 구성을 조정한다.

성찬 기능이 비활성화된 환경에서는 빈 메뉴를 노출하지 않는다. 권징·당회 메뉴도 기능이 준비되기 전에 회색 잠금 메뉴로 상시 전시하지 않는다.

### 5.2 중장기 구조

```text
RAAH · 목양 작업대
  오늘의 목양
  성도와 가정
    성도 / 가정 / 세례·입교 기록
  목양
    기록 / 성찬 목양 / 정기심방 / 후속 돌봄
  예배와 교육
    공예배 기록 / 교리교육
  일정
  관리
    접근 권한 / 감사 기록 / 이전 기록
  당회 · 권징과 회복   [정식 위임 및 별도 개발 이후]
```

기술적으로는 기능별 상세 화면과 URL 상태를 연결한다. 탭 이동 후 돌아오면 선택한 주기·성도·필터·스크롤 위치를 복원한다. URL에는 불투명 ID만 쓰고 이름·기도 제목·목양 내용은 넣지 않는다.

### 5.3 홈의 우선순위

홈 상단은 `이번 주 출석률`보다 `내가 오늘 해야 할 돌봄`을 먼저 보여 준다. 성찬 목양이 진행 중이면 해당 주기, 아직 대화를 시작하지 않은 대상, 약속된 심방, 내가 맡은 후속 돌봄을 보여 준다. 최근 기록과 통계는 아래로 내린다.

완료율은 목양 진행 현황일 뿐 영적 준비율이 아니다. 카드 이름을 `성찬 준비율 80%` 대신 `목양 확인 8명 / 대상 10명`으로 쓴다. 전체 회중의 영적 상태를 숫자로 대표하지 않는다.

## 6. 성찬 목양의 제품 개념

성찬 목양은 다음 세 개체를 분리한다.

| 개체 | 의미 | 예 |
| --- | --- | --- |
| 성찬 시행 | 실제로 성찬을 시행하는 예배 | 특정 주일 오전예배 |
| 목양 주기 | 일정 기간 성도들을 살피는 업무 묶음 | 이번 성찬 준비 또는 가을 정기 목양 |
| 개인 목양 | 그 기간에 한 사람과 나눈 대화·권면·후속 돌봄 | 대화 한 번 또는 여러 차례 심방 |

P1A에서는 시행 하나와 주기 하나를 연결하는 화면만 먼저 만든다. 데이터 구조는 한 주기에 여러 성찬 시행을 연결할 수 있게 한다. P1B에서 정기적인 목양 기간과 자주 시행하는 성찬을 연결하는 UI를 연다.

성찬을 매주 시행한다고 해서 매주 전 교인에게 같은 문답을 다시 시행하지 않는다. 이전 목양 기록을 참고할 수 있지만 자동으로 이번 목양을 완료 처리하지 않는다. 담당자가 기록을 재검토했다면 원래 대화일과 이번 검토일, 재참고 근거를 따로 남긴다.

### 6.1 대상자 선정

기존 `active` 상태는 성찬회원 여부가 아니다. 이름·나이·직분·과거 성찬 체크만으로 성찬회원 명부를 자동 확정하지 않는다.

성찬회원 정보가 확인된 사람을 후보로 제시하고 담당자가 주기 명부를 확정한다. 미확인 정보는 별도 확인 목록에 남긴다. 명부 미확인은 성찬 참여 금지를 뜻하지 않으며, 목양 대화 대상에서 그 사람을 제외하는 이유도 아니다.

새로 등록한 성도, 입교 준비자, 방문 교인, 장기 질병 중인 성도는 서로 다른 돌봄 맥락으로 표시한다. 준비자와 방문자는 일반 회원과 동일한 참여 승인 상태로 자동 취급하지 않는다.

### 6.2 주기 설정

필수 입력은 주기 이름, 시작일·종료일, 담당자, 교회가 채택한 안내문 버전이다. 성찬 시행일·예배 연결, 특별심방 마감일, 참고할 출석 기간은 선택 입력이다. 시간대 기본값은 한국 운영을 위한 `Asia/Seoul`이며 설정으로 명시한다.

`D-21에 시작` 같은 일정은 선택 템플릿이지 교리적 의무가 아니다. 성찬 시행이 취소·연기되면 관련 일정을 확인하도록 하되 목양 기록과 진행 중 돌봄을 삭제하지 않는다.

## 7. 성찬 목양의 실제 업무 흐름

### 7.1 시작과 준비

담당자는 홈에서 주기를 만들고 대상 명부를 확인한다. 사람을 선택하면 최근 확인된 세례·입교 정보, 조회 기간이 명시된 예배 기록, 지난 심방 날짜, 접근 권한이 있는 미완료 돌봄을 한 화면에 모아 보여 준다.

과거 민감 본문은 기본적으로 접는다. 목록을 여는 것만으로 전체 심방 본문을 일괄 복호화하지 않는다. 기존 기록에서 성찬 목양을 시작할 수도 있고 성찬 목양에서 기존 기록을 연결할 수도 있다.

### 7.2 심방 약속

`심방 약속`은 기존 사역 일정에 연결한다. 일정 등록이 곧 대화 완료는 아니다. 취소나 연기는 사유를 선택 또는 최소 기록하고 개인 목양 상태를 보존한다.

외부 캘린더 내보내기는 별도 확인을 거친다. 제목은 `목양 일정` 같은 중립 문구를 사용한다. 이름·기도 제목·죄 문제·공식 검토 사유를 설명, 장소, 링크 매개변수 또는 알림에 넣지 않는다.

### 7.3 대화와 권면

목양자는 질문 안내를 참고하되 모든 항목을 기계적으로 완료할 필요가 없다. 대화에서 실제로 들은 내용, 목양자의 해석, 전한 말씀과 권면, 함께 기도한 내용, 다음 돌봄을 구분해 기록한다.

대화 중 입력은 선택이다. 최소 메모 후 나중에 정리하는 사용도 지원한다. 현재 긴 메모 옮기기 흐름을 재사용하되 외부 AI 전송 기능으로 바꾸지 않는다.

### 7.4 정리와 후속 돌봄

저장 시 `목양 대화 확인`과 `후속 돌봄 필요`를 별도로 기록한다. 위로와 권면을 충분히 나눈 뒤에도 추가 돌봄은 남을 수 있다. 반대로 심방이 예정되었다고 영적 문제가 있다고 간주하지 않는다.

후속 돌봄에는 담당자, 다음 확인일, 구체적인 행동, 원본 기록 연결을 둔다. 예를 들어 `다음 주에 다시 만나 복음의 확신을 함께 살피기`는 비공개 본문에 기록하고 목록용 제목은 `후속 면담`으로 제한할 수 있다.

### 7.5 교회 권한자의 확인이 필요한 사안

현재 사용자에게 정식 판단 권한이 없으면 `권한자 확인 필요`라는 제한된 내부 메모와 후속 과제를 남긴다. 그 표시만으로 성찬 참여 제한, 권징 개시, 공개 경고를 발생시키지 않는다. 민감한 확인 요청은 당회원 등 승인된 범위 밖에 표시하지 않는다.

향후 공동 목양에서 교회 권한자에게 자료를 전달할 때는 공유할 내용과 수신자를 다시 확인한다. 전체 상담 원문을 일괄 넘기는 것을 기본으로 하지 않는다.

### 7.6 성찬 시행 후

실제 참여 사실을 기존 예배 기록과 연결하되 목양 진행 상태를 자동 완료하지 않는다. 불참은 질병·여행·다른 사정·미확인 등 맥락을 확인할 필요가 있을 뿐 자동적인 불순종 판정이 아니다.

성찬 후에는 감사와 위로, 계속 살펴야 할 어려움, 남은 약속을 확인한다. 대요리문답 175문은 성찬 후의 성찰도 다루므로, 제품 흐름 역시 당일 참석 체크로 끝나지 않도록 한다. [T3]

주기를 마감하더라도 미완료 과제는 후속 돌봄 목록에 남긴다. 다음 주기로 옮길 때 기존 과제를 복제하지 않고 연결만 추가한다.

## 8. 상태 모델: 반드시 세 축을 분리한다

### 8.1 목양 진행 상태

| 내부 값 | 화면 이름 | 의미 |
| --- | --- | --- |
| `not_started` | 미확인 | 이번 주기의 대화·검토를 시작하지 않음 |
| `scheduled` | 심방 예정 | 약속이 있으며 아직 목양 확인 전 |
| `in_progress` | 대화 진행 중 | 추가 대화나 정리가 진행 중 |
| `reviewed` | 목양 확인 | 담당자가 대화 또는 허용된 기존 기록 재검토를 확인함 |
| `closed_without_contact` | 연락 미성사로 종료 | 이유를 기록하고 해당 주기의 접촉 시도를 종료함 |

일반 흐름은 `not_started → scheduled → in_progress → reviewed`다. 즉석 심방은 예정 단계를 건너뛸 수 있다. 일정 취소는 완료가 아니다. 완료 후 재개는 가능하되 재개 사유와 변경 이력을 남긴다. `closed_without_contact`를 목양 확인 인원에 합산하지 않는다.

### 8.2 별도의 후속 돌봄 상태

과제는 `open / deferred / done / cancelled`를 가진다. 목양 확인 상태와 별개이므로 `reviewed + open task`가 가능하다. 여러 과제가 존재할 수 있고, 완료한 과제를 다시 열 때도 이력을 보존한다.

홈의 `추가 돌봄 필요` 수치는 권한 내 미완료 과제가 있는 사람 수다. 미확인·심방 예정·목양 확인 인원과 중복될 수 있음을 명시한다. 중복되는 숫자를 합쳐 전체 대상 수처럼 표시하지 않는다.

### 8.3 교회의 공식 기록과 실제 참여 사실

성찬회원 등록, 교회가 정식으로 기록한 제한, 실제 성찬 참여는 별도 정보다. 공식 제한의 사유는 일반 목양 목록에 노출하지 않는다. P1에서는 기존 문서의 제한된 참조만 허용하고, 새 정지·복권 결정을 만드는 기능은 제공하지 않는다.

실제 참여 상태는 `참여 확인 / 미참여 확인 / 미기록 / 해당 예배에 성찬 없음`으로 구별한다. 과거 `false` 값만 남아 있는 자료는 누가 언제 확인했는지 검증할 수 없다면 `이전 형식 기록`으로 표시한다. 과거 자료를 일괄 재해석해 결석·참여 거절·불신앙을 만들어 내지 않는다.

## 9. P1 화면별 상세 요구사항

### 9.1 성찬 목양 주기 목록

진행 중·예정·마감 주기를 나눈다. 각 카드에는 기간, 연결된 성찬 시행일, 대상 수, 목양 확인 수, 다음 할 일을 표시한다. 권한이 없는 주기는 이름과 수치도 반환하지 않는다.

### 9.2 주기 작업 화면

```text
성찬 목양 / 가을 목양 주기
연결된 성찬: 등록된 시행일    담당: 나

이번 주기: 12명
미확인 4 / 심방 예정 3 / 대화 진행 1 / 목양 확인 4
추가 돌봄 3명  [위 진행 상태와 중복되는 별도 집계]

[이름 검색] [내 담당] [진행 상태] [다음 확인일]
성도 | 최근 대화 | 이번 목양 | 다음 약속 | 열기
```

이름순·다음 약속순·최근 접촉일순 정렬을 제공한다. `영적으로 위험한 순` 정렬은 없다. 로딩 상태·빈 명부·조회 오류·권한 없음은 다른 화면이다.

### 9.3 개인 목양 화면

데스크톱은 왼쪽 명부와 오른쪽 개인 작업 영역을 사용한다. 모바일은 개인 화면으로 전환하고 뒤로 가면 목록 상태를 복원한다.

개인 작업 영역의 순서는 `기본 정보 → 참고할 예배·심방 사실 → 대화 안내 → 기록 → 후속 돌봄`이다. 화면 상단에 `이 상태는 목양 진행 표시이며 성찬 참여 판정이 아닙니다`를 짧게 표시한다.

주요 행동은 `심방 약속`, `대화 기록`, `기존 기록 연결`, `후속 돌봄 추가`, `목양 확인`이다. 성도 A를 보다가 B를 선택하면 A의 민감 본문을 즉시 비우고 B의 권한을 새로 확인한다.

### 9.4 기록 편집 화면

필수 항목은 대상자, 대화일, 실제 대화·권면에 대한 최소 기록이다. 질문별 답변과 기도 제목은 권장하되 빈칸을 채우려고 내용을 지어내도록 강제하지 않는다. 기존 일반 심방 양식의 필수값을 변경할 경우 별도 회귀 검증을 한다.

편집 중 다른 성도·주기로 이동하거나 창을 닫으려 하면 미저장 경고를 표시한다. P1A에서는 명시적 저장을 우선한다. 평문 localStorage 임시저장과 오프라인 자동 저장은 제공하지 않는다. 서버 암호화 초안이 필요하면 별도 과제로 설계한다.

### 9.5 주기 마감 화면

대상 변동, 목양 확인 인원, 연락 미성사, 남은 과제를 구별해 확인한다. 마감 사유와 담당자, 시점을 남긴다. 공식 성찬 허용자 명단이나 권징 보고서를 자동 생성하지 않는다. 다운로드·인쇄는 P1A에서 제외한다.

## 10. 성찬 목양 대화 안내 초안

아래 질문은 고백문을 그대로 번역한 것이 아니라 제품에 넣기 위한 목양용 초안이다. 기본 근거는 소요리문답 97문, 하이델베르크 81–82문, 대요리문답 171–175문과 개혁교회의 성찬 예식문이다. 실제 사용 전 교회의 목양 책임자가 표현을 검토한다. [T1][T2][T3][T6]

| 주제 | 대화의 출발점 | 목양자가 남길 수 있는 기록 |
| --- | --- | --- |
| 복음과 그리스도 | 하나님 앞에 나아갈 때 무엇을 의지하고 계십니까? | 이해한 복음, 함께 확인한 약속의 말씀 |
| 회개와 새 순종 | 주님 앞에서 돌이키고 싶은 일과 도움이 필요한 일이 있습니까? | 자발적으로 나눈 내용, 구체적인 권면 |
| 연약함과 확신 | 성찬에 나아가는 일을 두렵게 하거나 주저하게 하는 것이 있습니까? | 낙심의 맥락과 복음의 위로 |
| 말씀과 예배 | 공예배와 말씀을 듣는 생활에 어떤 유익이나 어려움이 있습니까? | 실제 장애물과 교회의 돌봄 필요 |
| 사랑과 화목 | 교회나 이웃과의 관계에서 함께 기도하고 도울 일이 있습니까? | 안전하게 다룰 관계 문제와 다음 행동 |
| 가정과 교육 | 가정에서 말씀과 기도를 나누는 데 어떤 도움이 필요합니까? | 가정의 형편과 교육 지원 |
| 기도와 고난 | 지금 함께 기도하며 곁에 있어야 할 어려움은 무엇입니까? | 기도 제목과 실제 지원 |
| 성찬 후의 생활 | 성찬을 통해 받은 위로와 계속 붙들고 싶은 말씀은 무엇입니까? | 감사와 지속적인 돌봄 |

질문별 상태가 필요하면 `이번 대화에서 다룸 / 다음 대화로 남김 / 이번 대화에서 해당 없음`만 사용한다. 이는 대화 범위 표시이며 믿음·회개·순종의 합격 여부가 아니다. 질문을 다뤘다는 체크가 자동으로 개인 목양을 완료시키지 않는다.

기록은 `관찰한 사실 / 본인이 말한 내용 / 목양자의 해석 / 전한 말씀과 권면 / 다음 행동`을 구분하도록 돕는다. 아직 확인되지 않은 진술은 사실로 확정하지 않는다. 죄의 세부를 불필요하게 수집하거나 모든 고백을 문서화하도록 강요하지 않는다.

화목에 관한 질문으로 피해자에게 가해자와의 즉시 대면·접촉을 요구하지 않는다. 안전 문제가 있는 상황은 일반적인 관계 회복 과제와 별도로 다룬다. 앱은 위기 대응·전문 상담·관계 기관의 절차를 대신하지 않는다.

## 11. 후속 기능의 구체적 범위

### 11.1 언약 가정과 정기 가정심방 — P2

`가정`에는 구성원 관계, 함께 거주하는지 여부, 목양 담당자, 마지막 가정심방, 다음 확인일을 둔다. 동일 성·주소만으로 가족을 자동 묶지 않는다. 구성원 관계와 거주 관계를 구분하고 각 개인의 기록·권한을 유지한다.

가정심방 계획은 주기, 대상 가정, 담당자, 약속, 실제 방문, 후속 돌봄을 관리한다. 전 가정을 순환해 돌볼 수 있도록 아직 방문하지 않은 가정을 보여 주되 방문 공백을 신앙 저하로 해석하지 않는다.

한 번의 가정심방을 여러 구성원의 돌봄과 연결할 수 있다. 원문을 사람마다 복사하지 않고 참가자 연결을 사용한다. 배우자의 내밀한 이야기가 가족 전체 화면에 자동 공개되어서는 안 된다.

화면에는 가정예배의 빈도 경쟁보다 실제 어려움과 도움을 남긴다. `매일 100점` 같은 가정 신앙 등급은 만들지 않는다. 기존 다음세대·말씀열매 데이터를 자동 가져오지 않으며, 그 서비스와의 연동은 목적·권한·동의를 따로 검토한다.

완료 기준: 독신 가정, 비신자 가족, 두 거주지에 관계된 자녀, 가족 중 일부만 심방한 경우에도 과도한 공개나 기록 중복 없이 처리된다.

### 11.2 세례·교리교육·입교 — P3

세례 여부와 종류, 신앙고백·입교, 성찬회원 등록을 별도 사건으로 남긴다. 모든 사람에게 `유아세례 → 입교` 경로를 강제하지 않는다. 성인 회심·세례, 유아세례 후 입교, 타 교회 전입, 증빙 미확인의 경로를 지원한다.

교육 과정은 교리문답 문항·수업·담당자·배운 내용·다음 대화를 기록한다. 교육 이수 버튼이 당회 문답 통과나 성찬회원 등록으로 이어지지 않는다. 공식 변화는 권한 있는 확인 및 근거 기록을 요구한다.

아동·청소년의 질문과 성장을 성인 심방의 죄 문제 기록과 같은 공개 범위로 처리하지 않는다. 보호자 관계가 있다고 해서 모든 개별 목양 기록에 접근 권한이 생기지 않는다.

완료 기준: 세례·입교 사실을 모르는 기존 성도는 미확인 상태로 유지되며, 나이와 교육 출석으로 자동 승격되지 않는다.

### 11.3 말씀과 기도를 목양에 연결 — P3

기록에 선택적으로 성경 본문, 교리문답 문항, 전한 권면, 함께 기도한 제목, 다시 살필 질문을 연결한다. 본문·고백문은 검토된 참조 목록을 사용한다. 앱이나 AI가 하나님의 개인적 지시를 만들어 내는 기능은 없다.

기도 제목은 원본 기록의 접근 권한과 보존 정책을 따른다. 당사자 이름을 지웠다고 교회 전체 기도 제목으로 자동 전환하지 않는다. 공유용 기도 제목은 작성자가 별도로 정리하고 수신 범위를 확인해야 한다.

목양이 설교와 교육에 주는 통찰은 우선 목양자가 직접 작성한 비식별 회고만 지원한다. 민감 원문을 외부 LLM에 보내 주제를 추출하거나 구체적 사례를 설교 예화로 자동 재사용하지 않는다.

집계 기능은 후순위다. 소규모 공동체에서는 이름을 지워도 특정인을 알아볼 수 있으므로, 희소 주제·날짜·가정·소수 집단의 조합을 노출하지 않는다. 단순한 최소 인원 기준만으로 익명성이 보장된다고 표시하지 않는다.

### 11.4 장로 공동 목양 — P4

실제 위임을 받은 직분자별로 담당 범위와 기간을 부여한다. 담당 교체 시 명부와 진행 중 과제는 인수인계하되 과거 모든 비밀 상담 원문을 자동 공개하지 않는다. 전체 회중 또는 다른 담당자의 민감 기록을 검색하는 기능도 기본적으로 차단한다.

공유할 내용은 일반 목양 요약, 담당 범위의 기록, 특별히 제한된 기록으로 나눈다. 누가 언제 열고 수정·공유했는지 감사 기록을 남긴다. 직무 종료·권한 회수는 다음 요청부터 적용하며 열려 있던 민감 화면도 정리한다.

공동 편집은 버전 충돌을 감지하고 마지막 저장이 다른 사람의 기록을 조용히 덮어쓰지 않도록 한다. 공식 결정은 특정 개인의 완료 버튼이 아니라 정해진 기관의 결정과 근거를 연결한다.

### 11.5 권징과 회복 — P5, 현재 구현 제외

권징은 단순 사건 CRM이나 처벌 점수 체계로 만들지 않는다. 신앙고백 30.3의 회복·거룩함·교회의 보호라는 목적을 참조하되, 실제 절차는 소속 교회의 헌법·권징조례를 기준으로 별도 검토한다. [T4]

향후 검토 대상은 권면 기록과 정식 사건의 구별, 관할과 권한, 제척·회피, 통지, 진술·자료, 회의록, 결정, 이의·상소, 재검토, 회복과 복권이다. 모든 사건에 같은 단계를 자동 진행시키지 않는다.

`심방 문제 발견 → 권징 사건 자동 생성`은 금지한다. 앱이 심각도·유죄·회개 여부·책벌을 판단하거나 추천하지 않는다. 서명·정족수·공식 기록 관리 등은 해당 교회의 절차가 확정된 뒤 설계한다.

현재 확보할 것은 기록 식별자, 접근 통제, 이력, 근거 참조의 확장 가능성뿐이다. 권징 테이블과 화면을 미리 배포하지 않는다. 안전이나 법적 대응이 필요한 사안을 교회 내부 절차가 끝날 때까지 미루도록 설계하지 않는다.

## 12. 데이터 모델 제안

아래 이름은 구현 예정안이며 현재 존재하는 테이블이라는 뜻이 아니다. SQL은 개발 시점의 최신 스키마를 다시 확인해 작성한다.

### 12.1 P0–P1의 최소 모델

| 구조 | 핵심 필드 | 역할 |
| --- | --- | --- |
| `raah_workspace_access` 신규 | `workspace_id`, `firebase_uid`, 직무, 허용 범위, 활성 여부, 위임·만료 시점 | RAAH 전용 접근 승인 |
| `raah_member_ecclesial_profiles` 신규 | `workspace_id`, `member_id`, 세례·신앙고백·성찬회원 등록 사실, 확인 시점·근거 | 현재 `active` 상태와 구별되는 교회적 기록 |
| `raah_communion_periods` 신규 | 기간, 이름, 상태, 설정·질문 템플릿 버전, 담당자 | 목양 주기 |
| `raah_communion_occasions` 신규 | `period_id`, 시행일, 연결된 `attendance_event_id`, 시행·취소 상태 | 실제 성찬 시행 |
| `raah_communion_reviews` 신규 | `period_id`, `member_id`, 담당자, 진행 상태, 명부 포함 상태, 버전 | 개인별 주기 진행 |
| `raah_communion_review_logs` 신규 | `review_id`, `visitation_log_id`, 연결 시점·연결자 | 여러 대화와 기존 기록 연결 |
| `raah_care_tasks` 신규 | 원본 참조, 담당자, 기한, 상태, 중립 제목, 암호화 상세, 일정 연결, 버전 | 주기를 넘어서 지속되는 후속 돌봄 |
| `raah_audit_events` 신규 | 행위자, 대상 종류·ID, 행동, 시점, 결과, 요청 ID | 열람·수정·공유·권한 변경의 감사 |
| `raah_idempotency_keys` 신규 | `workspace_id`, 행위자, 키, 요청 해시, 결과 참조, 생성 시점 | 생성 요청 중복 방지(12.5) |

초기 `workspace_id`는 서버가 선택하는 단일 교회 범위다. 멀티테넌트 판매·가입·결제 시스템을 이번에 만들지 않는다. 다른 교회 자료를 수용하기 전에는 기존 테이블 전체의 범위 구분, 외래키, 유일성, 저장·복구 경계를 별도로 검증해야 한다.

### 12.2 기존 기록을 확장하는 방식

성찬 문답 본문은 기존 `raah_visitation_logs`의 민감 본문 저장 경로를 재사용한다. 새로운 암호화 본문 버전에 `careKind`, 질문별 메모, 전한 말씀, 기도, 다음 행동을 넣을 수 있다. 주기 테이블에 같은 본문을 중복 저장하지 않는다.

`publicSummary`는 UI에서 `목록용 요약`으로 설명한다. 이것이 전체 공개 정보라는 뜻도, 암호화 본문과 동일하게 보호된다는 뜻도 아니다. 목록용 요약에는 민감한 내용을 적지 않도록 안내하고 서버에서 노출 범위를 통제한다.

`care_kind`, `owner_uid`, 접근 범위, `revision` 등 필요한 메타데이터를 기존 기록에 추가한다. 새 본문 버전과 암호화 알고리즘 버전은 구별한다. 암호화 함수 추출 과정에서 기존 키·암호문 포맷을 바꾸지 않는다.

### 12.3 교회적 기록의 정확성

세례 상태는 `미확인 / 미세례 / 세례 확인`, 신앙고백은 `미확인 / 준비 중 / 확인`, 성찬회원 등록은 `미확인 / 미등록 / 등록 확인`처럼 별개 축으로 둔다. 공식 제한의 존재와 사유는 별도 제한 영역에서 다룬다.

`등록 확인`만으로 현재 성찬 참여 허용을 자동 산출하지 않는다. `제한 기록 없음`도 교회가 공식적으로 무제한 참여를 승인했다는 뜻으로 표시하지 않는다. 확인 날짜와 출처를 함께 보여 준다. 정보의 정정은 이력을 남긴다.

### 12.4 제약과 일관성

`(workspace_id, period_id, member_id)`는 유일해야 한다. 명부를 다시 불러와도 개인 목양이 중복 생성되지 않아야 한다. 대상 제외는 행 삭제보다 제외 이력을 남기고 마감 당시의 집계가 재현되게 한다.

출석은 `member_id`와 예배 ID로 연결한다. 이름은 표시용이며 같은 이름의 성도를 병합하는 키가 아니다. 기존 이름만 있는 기록은 확인 작업을 거쳐 연결하며 자동 병합하지 않는다.

기록·주기·성도·과제를 연결할 때 동일한 범위에 속하는지 서버와 DB 제약으로 검증한다. 형식이 UUID라는 이유만으로 유효한 접근 대상으로 신뢰하지 않는다.

날짜는 교회 기준의 달력 날짜와 UTC 시각을 구분한다. 시행일·심방일은 지역 날짜, 감사·저장 시각은 UTC로 저장한다. 이름·생년월일·민감 요약을 중복 제거 키로 쓰지 않는다.

동시 저장은 `expectedRevision` 또는 동등한 낙관적 잠금으로 처리한다. 생성 요청은 서버에 보존되는 멱등 키로 중복을 막는다. 수정·과제 생성·감사 기록이 함께 필요한 작업은 DB 트랜잭션으로 수행한다. REST 호출을 여러 번 보내는 것만으로 원자성이 생긴다고 가정하지 않는다. 구체적인 방식은 12.5에서 정한다.

### 12.5 트랜잭션 구현 방식 — 확정

현재 구조(Netlify Function → Supabase REST, `service_role`)에서 여러 쓰기를 묶는 방법은 PostgreSQL 함수를 만들고 `POST /rest/v1/rpc/<함수명>`으로 한 번에 호출하는 것이다. PostgREST는 RPC 호출 하나를 하나의 트랜잭션으로 실행하므로 함수 안의 오류는 전체를 롤백한다. 직접 Postgres 연결(`pg` 드라이버·커넥션 풀)은 서버리스 연결 관리와 비밀값이 늘어나므로 도입하지 않는다.

역할 분담은 다음과 같다.

| 단계 | 위치 | 내용 |
| --- | --- | --- |
| 신원·접근 승인 확인 | Netlify Function | Firebase 토큰 검증, `raah_workspace_access` 조회, 요청 대상의 범위 확인 |
| 입력 검증·암호화 | Netlify Function | 스키마 검증, 민감 본문을 기존 AES-GCM 경로로 암호화. **키는 DB로 보내지 않는다** |
| 원자적 쓰기 | Postgres 함수(RPC) | 암호문·메타데이터 저장, 버전 확인, 연결 행 생성, 감사 이벤트, 멱등 키 기록을 한 트랜잭션에서 수행 |
| 응답 가공 | Netlify Function | 최소 DTO로 변환, 오류 코드 매핑 |

Postgres 함수 규칙:

- 함수는 전용 스키마(예: `raah_private`)에 두거나, `public`에 두더라도 `revoke execute ... from public, anon, authenticated` 후 `service_role`에만 `grant execute` 한다. 브라우저 키로 호출할 수 없어야 한다.
- `security invoker`를 기본으로 하고 `set search_path = ''`로 고정하며 객체 이름을 스키마까지 명시한다.
- 행위자 UID와 `workspace_id`는 서버가 검증한 값을 인자로 넘긴다. 함수는 이 값으로 `raah_workspace_access`를 다시 조회해 활성·만료 여부와 대상 범위를 **한 번 더** 확인한다. 서버 확인과 쓰기 사이에 권한이 회수되는 경합을 이것으로 막는다.
- 낙관적 잠금은 `update ... where id = $1 and revision = $2` 후 영향 행이 0이면 `raise exception using errcode = 'P0409'`처럼 고정된 SQLSTATE로 알린다. 서버는 이를 HTTP 409로 매핑한다. 권한 거절(`P0403`), 상태 전이 오류(`P0422`)도 같은 방식으로 정한다. 예외 메시지에 본문·이름을 넣지 않는다.
- 멱등성은 `raah_idempotency_keys(workspace_id, actor_uid, key, request_hash, result_ref, created_at)`에 유일 제약을 두고 같은 트랜잭션에서 기록한다. 같은 키에 다른 요청 해시가 오면 422로 거절한다. 오래된 키는 보존 정책에 따라 정리한다.
- 감사 이벤트 저장이 실패하면 함수 전체가 실패한다(14.5).

한계와 보완:

- 복호화가 필요한 **읽기**는 트랜잭션이 필요 없으므로 기존처럼 REST 조회 후 서버에서 복호화한다. 단, 민감 본문 열람 감사 기록은 조회 성공 후 별도 RPC로 남기며, 감사 기록이 실패하면 본문을 응답하지 않는다.
- 함수 로직이 SQL에 들어가므로 단위 테스트만으로는 검증할 수 없다. R00b의 로컬 Supabase(`npm run test:db`)에서 함수별 성공·롤백·권한 거절·충돌 테스트를 작성한다.
- 마이그레이션은 `supabase/migrations/`에 날짜 접두 SQL로 추가하고, 함수 변경은 `create or replace` 대신 버전을 올린 새 함수와 호출부 교체로 진행해 구형 서버 버전과의 호환 창을 둔다.

## 14. 보안·비밀보장 설계

### 14.1 권한 매트릭스

| 주체 | 일반 목양 진행 | 민감 본문 | 교회 공식 결정 |
| --- | --- | --- | --- |
| 승인된 목양자 | 실제 위임 범위 | 본인 및 명시적으로 허용된 기록 | 정식 권한·근거가 있는 범위만 |
| 담당 장로, P4 이후 | 배정된 대상과 공유된 범위 | 해당 직무에 필요한 승인 범위 | 정해진 기관·절차에 따라 |
| 홈페이지 기술 관리자 | 기본 접근 없음 | 기본 접근 없음 | 접근 없음 |
| 일반 회원·교사·학부모 | 접근 없음 | 접근 없음 | 접근 없음 |
| 향후 당회 서기 | 별도로 부여된 업무 범위 | 업무상 필요한 명시적 범위만 | 별도 공식 기록 권한 |

권한은 화면을 감추는 것만으로 구현하지 않는다. 각 API는 Firebase 신원과 최신 접근 승인, 대상 범위, 해당 필드의 열람 가능성을 검사한다. 관리 계정이라고 자신의 목양 권한을 일반 설정 화면에서 임의로 부여할 수 없게 한다.

기존의 목사·장로 계정이라고 과거 내밀한 기록 전체를 자동 공개하지 않는다. 과거 기록의 접근 범위를 확인할 수 없다면 더 제한된 상태로 이전하고 사람이 검토한다. 기록 작성자가 바뀌거나 퇴임해도 교회가 적법하게 관리할 자료와 개인적인 업무 메모를 무조건 동일하게 인계하지 않는다.

### 14.2 서버와 DB 경계

Supabase의 `service_role` 권한은 RLS를 우회할 수 있다. 따라서 현 구조에서 RLS 정책을 추가하는 것만으로 직분자별 격리가 완성되었다고 볼 수 없다. 서버에서 객체·필드별 권한을 확인해야 하며, RLS와 DB 권한은 직접 접근을 막는 추가 경계로 검증한다. [T7]

신규 민감 테이블은 브라우저용 역할의 직접 CRUD를 기본 거절한다. Firebase 사용자 신원과 Supabase `auth.uid()`가 자동으로 일치한다고 가정하지 않는다. 현재 서버 경유 방식을 유지하고, 향후 JWT 기반 DB 사용자 격리를 도입한다면 별도의 인증 설계를 검증한다.

초기에는 서버가 고정된 한 교회 범위를 선택한다. 사용자 요청의 `workspaceId`, `ownerUid`, 역할 문자열을 신뢰해 권한을 확대하지 않는다. 기존 RAAH API와 Firestore 구형 접근 경로에도 같은 제한 원칙을 적용해야 한다.

### 14.3 암호화와 메타데이터

민감 본문에는 질문 응답, 기도 제목, 죄 문제, 관계 문제, 공식 확인 필요 사유, 내밀한 후속 계획을 포함한다. 최소 목록 메타데이터에도 접근 권한을 적용한다. 암호화 여부만으로 정보 공개 가능성을 결정하지 않는다.

현재 서버 측 암호화는 종단간 암호화가 아니다. 서버와 키 관리자는 기술적으로 복호화할 수 있다는 한계를 운영 문서에 명시한다. 새로운 민감 기능에서도 사용자에게 서버조차 읽을 수 없다고 약속하지 않는다.

키·암호문·DB 백업을 분리해 관리하고 복구 시험을 한다. 키 교체는 별도 버전과 재암호화·복원 계획이 필요하다. 리팩터링 중 키를 새로 생성하거나 암호화 비밀값을 교체하지 않는다.

### 14.4 화면·로그·외부 전송

민감 API는 `Cache-Control: no-store`를 사용한다. 서비스 워커, 오프라인 캐시, 브라우저 영구 저장소에 평문을 남기지 않는다. 로그아웃, 세션 만료, 대상 전환 시 본문과 편집 메모를 정리한다. 공유 기기에는 일정 시간 비활동 후 본문 잠금과 재인증을 제안한다.

분석 SDK·오류 추적·세션 재생에는 입력값과 API 본문을 보내지 않는다. 자동 스크린샷이나 테스트 산출물에도 실제 자료를 사용하지 않는다. 외부 알림은 중립 문구만 표시하고 로그인 후 내용 확인으로 연결한다.

성찬·심방·권징 자료는 외부 AI 모델, 임베딩 서비스, 자동 요약으로 전송하지 않는다. 이름 삭제만으로 전송을 허용하지 않는다. 공개 교리 자료의 작성 보조와 개인 목양 데이터 처리는 별개로 취급한다.

### 14.5 감사와 보존

민감 본문 열람, 수정, 접근 승인·회수, 공유, 내보내기에 감사 이벤트를 남긴다. 감사 기록 자체에는 원문이나 민감 제목을 넣지 않는다. DB 관리자에 대한 완전한 불변성을 확보하지 않았다면 `변조 불가능`이라는 표현을 쓰지 않는다.

새 민감 기록에 필요한 감사 저장이 실패하면 성공으로 처리하지 않는다. 본문 저장과 감사 기록을 가능한 한 같은 트랜잭션으로 수행한다. 감사만 남고 본문이 없거나 반대인 상황의 복구 기준을 정한다.

보존 기간을 무조건 영구로 고정하지 않는다. 일반 목양 메모·교육 이력·교적 사실·공식 회의록은 목적과 보존 근거가 다르다. 실제 운영 전에 교회 책임자와 개인정보 담당 검토를 거쳐 정정·삭제·보존·백업 만료 정책을 확정한다. 이 문서는 법적 적합성을 판정하지 않는다.

## 15. 기존 자료 이전과 호환 정책

기존 명부·심방·출석·일정의 ID를 유지한다. 새 칼럼·테이블을 먼저 추가하고 구형 클라이언트도 읽을 수 있게 한다. 처음부터 기존 자료 전체를 새 스키마로 강제 변환하지 않는다.

세례·입교·성찬회원 필드의 초기값은 미확인이다. 과거 성찬 참여 체크나 `직분`으로 채워 넣지 않는다. 교회가 가진 원자료를 근거로 사람이 확인해 입력한다.

기존 후속 조치 완료 기록은 보존한다. 새 과제 모델로 옮길 때 `legacy source + id`의 유일성으로 중복을 막는다. 원문을 복제해 여러 군데 저장하지 않고 연결한다. 기존 완료 상태를 다시 미완료로 만드는 일괄 이전은 금지한다.

새 성찬 기능은 Supabase 준비 전에는 비활성화한다. 장애가 나면 조회·저장 불가와 재시도를 안내하며 Firestore 평문 쓰기로 우회하지 않는다. 기존 Firestore 호환 기능의 읽기·쓰기 정책은 권한·이전 검증을 거쳐 별도로 축소한다.

이전 순서는 `암호화 백업·키 복구 시험 → dry-run → 건수·외래키·권한 검증 → 승인된 소량 적용 → 확인 → 나머지 적용`이다. 이름·주소·기도 제목을 콘솔 출력이나 GitHub 이슈에 남기지 않는다. 신규 기능을 꺼도 새 기록이 사라지지 않게 하고, 되돌릴 때 보호 수준이 낮은 저장소로 이동하지 않는다.

| 가정심방에 일부 구성원만 참석 | 참가자만 기록 연결, 나머지 자동 완료 없음 |
| 교회 공식 확인이 필요한 사안 | 제한된 내부 처리, 공개 목록 노출·자동 책벌 없음 |
| 성찬 미참여 사실만 기록됨 | 거절·불순종·불신앙의 원인을 추정하지 않음 |

### 17.2 보안·데이터 관련 필수 시나리오

다른 사용자의 `reviewId`, `logId`, `memberId`, `workspaceId`를 대입해도 본문·요약·건수·기록 존재 여부가 새지 않아야 한다. 기술 관리자, 일반 회원, 권한 회수자, 만료 계정, 다른 담당자에 대해 허용·거절 테스트를 모두 작성한다.

두 창에서 같은 기록을 수정하면 두 번째 저장에 충돌을 알린다. 저장 요청을 반복해도 주기·대화·과제가 중복되지 않는다. 기록 저장 성공 후 과제 연결만 실패하는 부분 저장은 트랜잭션 또는 명시적 복구 상태로 처리한다.

로그아웃·세션 만료·성도 전환·탭 복귀 시 다른 사람의 본문이나 저장 전 메모가 나타나지 않는다. 새로고침 후 복원 가능 범위와 불가능 범위를 정확히 안내한다. 외부 캘린더·알림·오류 로그·분석 이벤트에는 민감한 내용이 없어야 한다.

틀린 암호화 키, 손상된 암호문, 누락된 접근 승인, Supabase 장애, 감사 기록 저장 실패에서 안전하게 거절한다. 이전 Firestore 경로로 새 성찬 기록을 저장하는 우회가 없어야 한다.

API 목과 메모리 DB 테스트만으로 PostgreSQL 제약·트랜잭션·RLS 검증을 대신하지 않는다. 별도의 격리된 실제 PostgreSQL/Supabase 테스트 환경에서 유일성·권한·동시성을 확인한다. 운영 자료나 운영 자격증명은 테스트에 사용하지 않는다. 환경 구성은 17.4를 따른다.

### 17.3 UI와 회귀 검증

360px·390px 모바일, 태블릿, 일반 데스크톱에서 핵심 흐름을 검증한다. 키보드 이동, 포커스, 상태 텍스트, 읽기 쉬운 버튼 크기를 확인한다. 색상만으로 상태를 구별하지 않는다.

기존 성도 수정, 예배 유형 전환, 출석 저장, 심방 복호화·수정, 일정 복사·수정·완료, 이전 기록 접근을 회귀 검증한다. 기준선의 기존 테스트와 다음 명령을 실행하고 결과를 기록한다.

```sh
npm run typecheck
npm run lint
npm test
npm run build
```

공통 Firebase 규칙이나 구형 접근 경로를 바꾸면 저장소의 에뮬레이터 기반 `npm run test:rules`를 추가한다. 필요한 환경을 준비하지 못했으면 미검증으로 표시한다. 배포 API의 익명 401만 확인하고 로그인 후 DB·복호화까지 검증했다고 기록하지 않는다.

### 17.4 DB 테스트 환경 (R00b) — 구성 완료

로컬 Supabase(OrbStack + Supabase CLI)로 확정했다. PostgREST·역할·RLS가 운영과 같은 구성이고, `supabase db reset`으로 매번 빈 DB에 전체 마이그레이션을 재적용할 수 있으며, 운영 자격증명과 섞일 여지가 없다.

- 스키마의 단일 원천은 `supabase/migrations/`다. 기존 루트 SQL은 순서가 있는 마이그레이션 파일로 옮겼다.
- `npm run test:db`는 로컬 DB를 초기화하고 `tests/db/`를 실행한다. 로컬 호스트가 아니면 실행을 거부한다.
- 일반 `npm test`에서 `tests/db/`는 환경변수 부재로 건너뛴다. Docker가 꺼져 있어도 기본 검증은 그대로다.
- 신규 RPC 함수·제약·권한 테스트는 모두 `tests/db/`에 추가하며, PR-3 이후 PR의 검증 목록에 `npm run test:db`를 포함한다.

세부 결과와 발견 사항은 [R00 기준선 기록](2026-09-28-raah-baseline-r00.md)에 있다.

## 18. 배포와 롤백

배포는 별도 사용자 승인과 PR 검토를 거친다. `main` 직접 push는 하지 않는다. API·스키마·화면을 한 번에 교체하지 않고 추가형 스키마, 호환 API, 비활성 화면, 검증, 제한 활성화 순서로 진행한다.

기능 플래그는 서버 권한 검사를 대신하지 않는다. 플래그를 끄면 신규 생성·수정을 차단하되 기존 기록의 보존과 승인된 조회 경로는 명확히 한다. 신규 API를 구형 화면에서 호출해도 권한이 약화되지 않아야 한다.

초기 시범은 합성 자료로 시작한다. 실제 자료는 교회가 허용한 범위에서만 입력한다. 출시 전 백업·키 복구, 권한 회수, 실패 상태, 담당자의 목양 문구 검토를 통과해야 한다.

롤백은 플래그·호환 서버 버전으로 수행한다. 새 자료를 삭제하거나 평문으로 변환하지 않는다. DB 되돌리기가 필요하면 생성된 자료의 보존 방법을 먼저 검증한다. 별도 승인 없이 운영 환경변수·외부 캘린더·공지·권한을 변경하지 않는다.

## 19. 성공 지표

제품 성공은 기록량 증가나 영성 점수 상승으로 측정하지 않는다. 다음은 측정 제안이며 아직 달성된 수치가 아니다.

| 평가 대상 | 검토할 질문 |
| --- | --- |
| 돌봄 누락 | 담당자가 잊고 있던 약속과 미확인 대상이 줄었는가? |
| 흐름 연결 | 성도 선택 후 대화 기록과 다음 약속까지 끊김 없이 갈 수 있는가? |
| 중복 입력 | 기존 심방·성도·일정을 다시 쓰지 않고 연결할 수 있는가? |
| 신학적 정확성 | 사용자가 목양 확인을 성찬 합격 판정으로 오해하지 않는가? |
| 비밀보장 | 허용되지 않은 계정에 본문·요약·민감 상태가 전혀 노출되지 않는가? |
| 운영 신뢰성 | 조회 실패·미기록·저장 충돌을 즉시 이해하고 복구할 수 있는가? |
| 현장 유용성 | 목양자가 대화 중 화면보다 사람에게 집중할 수 있는가? |

시범 종료 때 기능 수보다 위 질문에 대한 실제 관찰을 바탕으로 P1B 진입 여부를 결정한다. 출석률·성찬 참여율·교육 진도를 개인 간 신앙 순위로 보여 주지 않는다.
